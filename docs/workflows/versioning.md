# Versioning and releases

How the project versions code, generates the changelog, and publishes GitHub releases.

## Summary

Versioning is automated by [release-please](https://github.com/googleapis/release-please) from
Conventional Commits (already enforced by the `commit-msg` hook, see `AGENTS.md`). There's no
manual version bump: the version in `package.json`, `CHANGELOG.md`, and the GitHub tag/release
are all generated by the bot.

A single version covers the whole monorepo (client + server together) — there's no independent
per-app versioning.

## How commit type affects the version

| Commit type                                    | Effect on version |
| ----------------------------------------------- | ------------------ |
| `feat`                                          | **minor** (`0.1.0` → `0.2.0`) |
| `fix`, `perf`, `refactor`, `docs`, `chore`, ...  | **patch** (`0.1.0` → `0.1.1`) |
| `feat!` or a `BREAKING CHANGE:` footer           | minor while the project is on `0.x` (major from `1.0.0` onward) |

This is configured via `bump-minor-pre-major: true` in `release-please-config.json` — without
that flag, release-please would treat `feat` as a patch while the version is `0.x` (the tool's
default behavior pre-1.0).

## What shows up in the changelog

Not every commit that affects the version shows up in `CHANGELOG.md`. The visible sections are:

- **Features** (`feat`)
- **Fixes** (`fix`)
- **Performance** (`perf`)
- **Improvements** (`refactor`)

`docs`, `chore`, `test`, `build`, `ci`, and `style` commits still count toward whether the next
version is a patch, but they're hidden from the changelog (configured via `changelog-sections`
in `release-please-config.json`).

## Step-by-step flow

1. PRs are merged into `main` as usual, following Conventional Commits.
2. On every push to `main`, the `.github/workflows/release-please.yml` workflow runs and the
   release-please bot opens (or updates) a Pull Request named something like
   `chore(main): release 0.2.0`, accumulating every commit not yet released.
3. That PR already has `CHANGELOG.md` and the `package.json` version updated — just review the
   release notes.
4. Merging that release PR makes release-please:
   - create the Git tag (e.g. `v0.2.0`);
   - publish the GitHub Release with the generated notes;
   - close out the release PR (until the next push to `main` opens a new one).

No tag or release is created before that merge — while the release PR is open, other PRs can
keep merging into `main` normally; they just accumulate into it.

## Where to look

- Published releases: [GitHub Releases tab](https://github.com/kangeikailabsio/kangeikai/releases)
- Configuration: `release-please-config.json` and `.release-please-manifest.json` (repo root)
- **Never hand-edit `CHANGELOG.md` or the `version` field** — the bot manages both; any manual
  edit gets overwritten on the next release.
